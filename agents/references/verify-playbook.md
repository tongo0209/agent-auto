# Verify playbook — chi tiết (design-checker)

> Core `design-checker.md` giữ **toàn bộ luật cấm** dạng one-liner. File này là phần *bằng chứng đo đạc* + *ví dụ đầy đủ* + *bảng map tool*.
> Đọc khi: cần dựng lệnh browser cho tình huống lạ · một luật bị nghi ngờ · cần biết vì sao luật tồn tại. **KHÔNG đọc mặc định.**

## 1. Bảng map browserpilot ↔ Playwright MCP + triết lý gộp lô

### 🧭 Browser MCP — dùng browserpilot (MẶC ĐỊNH) HOẶC Playwright MCP (thay thế)

Recipe verify dưới đây viết cho **browserpilot** (gộp nhiều bước trong 1 `run_steps` = ít round-trip; có `read_signals` lọc sẵn console/network). Máy CHỈ có **Playwright MCP** (`mcp__playwright__browser_*`) → GIỮ NGUYÊN *mục tiêu* mỗi bước, đổi tool theo bảng; Playwright **mỗi action 1 call** (không gộp được như run_steps) nên tốn nhiều call hơn — chấp nhận, vẫn verify đúng. **Chỉ dùng 1 trong 2, KHÔNG trộn.** (Ưu tiên browserpilot nếu có cả hai.)

| Việc | browserpilot | Playwright MCP |
|---|---|---|
| Mở trang / reload | `run_steps[{goto}]` | `browser_navigate` |
| Đổi viewport PC↔mobile | `set_viewport` (+`then_reload`) | `browser_resize` → `browser_navigate` lại |
| Khẳng định render | `expect_visible` | `browser_snapshot` (element có trong cây) / `browser_wait_for{text}` |
| Khẳng định text/nội dung | `expect_text` | đọc `browser_snapshot` / `browser_wait_for{text}` |
| Thao tác click/fill | `click`/`fill` trong run_steps | `browser_click`/`browser_type`/`browser_fill_form` (cần `ref` từ snapshot) |
| Lỗi console | `read_signals` / `expect_no_console_errors` | `browser_console_messages` (lọc type=error) |
| 404 / network | `read_signals` | `browser_network_requests` (lọc status ≥ 400) |
| Chụp ảnh | `screenshot` | `browser_take_screenshot` |
| Đọc DOM/JS khi cần | `run_script` (tự-bound ⏱) | `browser_evaluate` |

Mọi LUẬT verify-nhẹ áp NHƯ NHAU bất kể MCP: layout/position đọc **CSS tĩnh + số học** (📐, KHÔNG đo live DOM), 404 phân loại 1 lần (🟡), uncaught-JS verify behavioral (🔴), widget có-trạng-thái so state trước≠sau (🔁). Playwright cũng là **1 browser process duy nhất** → song song nhiều checker vẫn theo CAP 2-3/đợt + flail-stop. Serve `dist/` bằng `npx --yes http-server` (cả 2 MCP đều mở qua URL `http://localhost:<port>/`). **Không có browser MCP nào** → ghi "chỉ check tĩnh trên code" (như cũ).


## 2. Bằng chứng đo đạc sau mỗi luật cấm

   ⛔ **CHỐNG SNOWBALL — `screenshot` hoặc `Read` ảnh FAIL (path sai / file không có):** DỪNG NGAY tại đó. **KHÔNG** đi tìm file ảnh thay thế, **KHÔNG** `find`/`ls`/`glob` `.png` trên `/tmp`, `/private/tmp`, `/var`, `~`… (sẽ vớ phải ảnh của session/việc KHÁC = noise, đốt nhiều call vô ích). Ghi vào report "không lấy được screenshot — render đã xác nhận qua `expect_visible`" rồi đi tiếp. Screenshot CHỈ là bằng chứng phụ; thiếu nó KHÔNG làm verify thất bại. (Một Read-ảnh fail KHÔNG được phép kéo theo bất kỳ lệnh tìm-file nào.)
   ❌ KHÔNG `Read` lại ảnh (render đã khẳng định bằng `expect_visible`; screenshot chỉ lưu bằng chứng), KHÔNG `inspect`/`run_script`, KHÔNG tách viewport thành nhiều `run_steps`. Mục tiêu **~5–6 tool-call/lượt** — đo thật: làm sai ≈ 20 call/138s, đúng recipe ≈ 6 call. (Trang H5 → 1 viewport ngang, recipe rút còn 1 `set_viewport`.)
   📐 **BUG layout/position/size (lệch · đè · rớt · sai kích thước — vd #2/#3/#10): verify bằng check TĨNH, KHÔNG đo live DOM.** Đọc giá trị trong **built CSS** (`dist/<name>.css` / `<name>-sprite.css`) rồi so với mốc tham chiếu bằng **số học** (vd `left + width` vs vị trí phần tử kế / biên section / canvas), cộng `expect_visible` + 1 screenshot làm bằng chứng. **CẤM `run_script`/`getBoundingClientRect`/`inspect` để đo toạ độ runtime** — giá trị nằm sẵn trong CSS tĩnh; đo live chỉ tốn call + dễ flail. (Đo thật trên clone cdn-source 2026-06-26: 1 bug position verify bằng run_script → ~7 call thừa toàn FAIL `document is not defined`/strict-mode; cuối cùng vẫn phải kết luận bằng đọc CSS + số học — thứ làm được từ ĐẦU.) **`expect_visible` KHÔNG phải bằng chứng VỊ TRÍ** — element off-screen (`right:-350px`) vẫn `visible`=true (Playwright chỉ kiểm tồn-tại/không-hidden/có-size, KHÔNG kiểm trong viewport), nó chỉ xác nhận RENDER. Verdict bug vị trí PHẢI tựa SỐ HỌC trên CSS tĩnh (vd `right:80px`+`width:250px` lọt trong biên phải = đạt; `right:-350px` = ngoài màn = FAIL) — ĐỪNG liệt `expect_visible` như bằng chứng đã-fix. (Đo thật demo-preregister 2026-06-26: bug gift `right:-350px`→`80px` PASS đúng nhờ đọc CSS tĩnh; `expect_visible` đi kèm PASS cả 2 trạng thái nên KHÔNG phân biệt được.)
   ⛔ **CHỐNG LẶP-FAIL run_script/extract:** lỡ gọi `run_script`/`extract` mà FAIL (`document is not defined`, "Selector không hợp lệ", strict-mode "resolved to N elements") → **DỪNG, KHÔNG gọi lại cùng kiểu**. Quay về check tĩnh (đọc CSS/HTML built) hoặc `expect_*` trong `run_steps`. (Đã thấy agent lặp `document is not defined` 2 lần liên tiếp = đốt call vô ích.)
   🟡 **404/network từ `read_signals` — PHÂN LOẠI 1 LẦN, KHÔNG săn lặp:** `read_signals` đã liệt kê đủ 404. Phân loại NGAY theo URL, **KHÔNG** `run_script` network-hunt lại để "cho chắc":
      - path asset **CỦA MÌNH** (`assets/.../*.png|jpg|svg`, path tương đối trong dist) → **liên quan bug**: đối chiếu source/dist **TĨNH** (grep tên file, `ls dist/...`), không cần runtime.
      - host **NGOÀI** (`cdn-mainsite-aka…`, CDN lib/swiper) hoặc `/video/*` → **noise môi trường** (lib từ CDN, video deploy riêng) → ghi 1 dòng "ngoài phạm vi" rồi BỎ QUA.
      (Đo thật cdn-source 2026-06-26: checker săn 404 lặp **8 `run_script`** để phân loại CDN-vs-bug = thừa; 1 lần đọc read_signals + phân loại theo pattern là đủ.)
   🔴 **BUG uncaught-JS-error ("Console đỏ", ReferenceError/TypeError lúc load — vd #6): verify BEHAVIORAL, CẤM reload-loop.** `read_signals`/`expect_no_console_errors` **KHÔNG bắt** uncaught exception (chỉ bắt `console.*` + network) — BIẾT RỒI, **đừng loop `run_script` đi săn pageerror**.
      - Verify bằng **HỆ QUẢ hành vi** qua `expect_*`: lỗi làm gãy gì thì khẳng định cái đó (vd shine chết → đếm `.MS__hover-shine canvas` > 0; handler gãy → thao tác rồi `expect_visible`). Rẻ + tin cậy; **board `Verify:` cấp sẵn assertion cụ thể (vd "canvasCount > 0") → THỰC THI thẳng, KHÔNG tự nghĩ lại; chỉ tự suy assertion khi board bỏ trống.**
      - **CHỈ khi bắt buộc** khẳng định console-clean: **ĐÚNG 1** `run_script` **bounded** — 1 `goto` + `page.on('pageerror')` + timeout ≤ 8s; **CẤM `reload`/`waitUntil:'load'`** (chờ video/resource → hang) và **CẤM lặp**. (Đo thật cdn-source 2026-06-26: 1 `run_script` reload-mobile bắt pageerror **treo 190s = 38% cả run** — đúng cái phải tránh.)
   🔁 **BUG widget CÓ TRẠNG THÁI (carousel/slider/tab/stepper/accordion/dropdown-đổi-layout — vd swiper, đổi đội hình): verify = TRẠNG THÁI ĐỔI (trước ≠ sau), KHÔNG phải "marker active còn đó".** Sau thao tác, khẳng định **danh tính MỚI** của phần tử active bằng `expect_attr`/`expect_text`/`expect_count` trong `run_steps` — vd click bullet thứ n → `expect_attr` `.swiper-slide-active` có `data-swiper-slide-index`=`n`; đổi dropdown đội hình → `expect_attr` `.builder__center--board` có `data-build`=`433`. **CẤM kết luận PASS chỉ vì `.x-active`/`expect_visible` vẫn true sau thao tác** — slide/tab CŨ vẫn visible khi click KHÔNG ăn ⇒ false-PASS. Tách 2 phần, phải có CẢ HAI: *init-proof* (class/bullet do widget sinh động tồn tại ⇒ khởi tạo OK) + *tương-tác-proof* (state ĐỔI). Không có attr ổn định để so → ĐÚNG 1 `run_script` bounded đọc index trước/sau (theo luật ⏱). (Đo thật demo-preregister 2026-06-26: checker kết luận swiper PASS bằng "slide-active vẫn visible sau click" = LỎNG; verdict đúng nhờ init-proof 9 bullet sinh động — phép chặt: active index `0`→`2` sau click bullet #2.)
   ⏱ **TIMEOUT/HANG — `run_script` là tool DUY NHẤT KHÔNG có timeout tool-level** (schema chỉ `{script,tab}`), nên nó hang là **treo cả run, không gì cắt được từ ngoài** (đo: 190s). `run_steps` thì bounded sẵn (`options.timeout_default` mặc định 5000ms/step + per-step `timeout`/`optional`/`continue_on_fail`) → **không thể treo lâu**. Nguyên tắc:
      - **Ưu tiên `run_steps` cho MỌI thao tác browser** — goto, đổi viewport, expect_*, screenshot đều làm được; nó tự bound.
      - **Đổi viewport / reload → LUÔN bằng `run_steps`** (`set_viewport`+`then_reload`), **KHÔNG** `page.reload` trong run_script (chính là cú treo 190s ở mobile). Browser-state nghi hỏng (tab chết) → `session reset` trước, đừng cố reload trong script.
      - **Buộc dùng run_script → TỰ bound TRONG script:** mọi `page.goto/reload/waitFor*/locator.*` PHẢI truyền `{timeout: ≤8000}`; navigation dùng `waitUntil:'domcontentloaded'` (**CẤM `'load'`** — chờ video/CDN → hang); bọc `try/catch` để fail thì RETURN; nên thêm guard `Promise.race([việc, new Promise((_,r)=>setTimeout(()=>r(Error('bounded')),8000))])` để dù quên timeout cũng không vượt 8s.
   📸 **CHỤP/CHECK-ẢNH theo LOẠI bug — KHÔNG chụp tràn.** Screenshot + Read-ảnh CHỈ có giá trị khi verdict phụ thuộc NHÌN pixel. Quyết theo tiêu chí verify của TỪNG bug:
      - **KHÔNG cần ảnh** (verdict = assertion/data → ảnh không giải đáp gì, **BỎ screenshot luôn**): `functional` (click/popup/form/đổi-ngôn-ngữ/nav/CTA) → `expect_*`; `content`/text → `expect_text`; uncaught-JS-error → behavioral `expect_*`/read_signals; `performance`/network/404 → read_signals; `visual-CSS` layout/position/size → static CSS + số học (📐).
      - **CẦN ảnh:** CHỈ bug **visual-design appearance** (màu / khoảng cách / "trông lệch so với thiết kế") **VÀ có baseline** → screenshot + Read so ảnh (theo 🚦). Không baseline → vẫn KHÔNG Read ảnh (chỉ chụp lưu nếu muốn).
      - **Bằng chứng:** tối đa **1 screenshot/viewport** nếu đợt CÓ bug visual/layout (đính report cho người liếc) — KHÔNG bắt buộc, KHÔNG Read lại. **Đợt TOÀN functional/content/console/network → 0 screenshot.** (Đừng nhét `screenshot` mặc định vào run_steps khi không có bug visual nào.)

## 3. Các bước runtime 5.1–5.5 — bản đầy đủ kèm ví dụ

   1. **Reset browser cho SẠCH trước khi mở trang** — `session reset` ngay ĐẦU verify: phiên có thể còn tab/viewport bẩn từ lượt verify trước hoặc agent khác → gây "tab chết" + recovery rất đắt (đo thật: browser hỏng ≈ **474s** so với ≈ 49s một lượt nhẹ sạch). **NGOẠI LỆ:** manager báo "đang chạy SONG SONG với checker khác" → **KHÔNG `reset`** (sẽ giết browser của lượt kia vì chung 1 instance), dùng `session new_tab` (`isolated`) thay thế. Sau đó serve bản build (chạy nền, nhớ kill sau khi xong): **ưu tiên `npx --yes http-server dist -p <port>`** — Node luôn có sẵn (repo build bằng npm) nên chạy được cả macOS lẫn Windows; máy có Python thì `python3 -m http.server <port>` / `python -m http.server <port>` (chạy trong `dist/`) cũng được — hoặc dùng URL dev server nếu manager đưa.
   2. Một lần `run_steps` để mở trang, khẳng định section chính render, bắt lỗi console và chụp ảnh — ví dụ:
      `{"steps":[{"goto":"http://localhost:<port>/"},{"wait_for":".hero"},{"expect_visible":".hero"},{"screenshot":"desktop-home"},{"expect_no_console_errors":true,"continue_on_fail":true}]}`
      Bước fail sẽ trả gói chẩn đoán (url, console, element gần giống, screenshot path) — ĐỌC gói đó trước, đừng vội `inspect` cả trang.
   3. `read_signals` để soi sâu console errors/warnings + network failures (ảnh 404, CDN lỗi) đã lọc sẵn — kết quả này là nguồn cho issue console/network.
   4. Test viewport theo **"Quy ước giao diện team" trong CLAUDE.md global** (nguồn luật DUY NHẤT: viewport PC/Mobile, reload 1 lần, H5 chỉ ngang, đóng/reset session sau test). Kỹ thuật thực hiện: gom cả 2 viewport vào CÙNG một `run_steps` bằng step `set_viewport` — chuyển PC → mobile reload đúng 1 lần vì JS layout/swiper init theo viewport lúc load:
      `{"steps":[{"set_viewport":{"width":1920,"height":1080}},{"goto":"..."},...check PC + {"screenshot":"pc-home"}...,{"set_viewport":{"width":768,"height":1024},"then_reload":true},...check mobile + {"screenshot":"mobile-home"}...]}`
      Spec yêu cầu breakpoint khác → check thêm tương tự (chú ý project dùng `orientation` media query — xem base-structure.md).
      **Ngoại lệ — trang H5** (webview in-game, khi spec/manager/user nói đây là trang H5): chỉ check **MỘT view duy nhất dạng ngang như PC (1920x1080)** — `set_viewport` 1 lần đầu run là đủ, KHÔNG check mobile, KHÔNG có màn chuyển viewport/reload.
   5. **(CHỈ khi CÓ ảnh design baseline — xem 🚦 CỔNG ĐẦU TIÊN; verify-nhẹ/bug-fixer KHÔNG baseline thì BỎ QUA bước này)** So screenshot với ảnh design: `screenshot` trả về **file path** (ảnh không vào context) → dùng tool `Read` mở **đúng path đó** (KHÔNG đoán path khác, fail thì theo luật CHỐNG SNOWBALL — không đi tìm file) khi cần đánh giá visual. Muốn xem DOM thực tế sau JS thì `inspect` (mode `text`/`full`).
   6. Lỗi console/network cũng là issue — phân loại như thường (uncaught error = blocker/major). **404 → phân loại 1 lần theo luật 🟡 (KHÔNG săn lặp); uncaught JS error → verify BEHAVIORAL theo luật 🔴 (KHÔNG loop run_script/reload bắt pageerror — đã treo 190s).**

## 4. Test chức năng — bản đầy đủ kèm ví dụ run_steps

6. **Test CHỨC NĂNG (tương tác thật — không chỉ đọc code)**:
   1. Lập danh sách hành vi từ: mục "States & Interactions" của spec + các hành vi chuẩn của landing game (popup mở/đóng, swiper trượt, đổi ngôn ngữ, CTA/link đúng đích, form validate, lazyload ảnh dưới fold).
   2. Với từng hành vi: gom thao tác + verify vào MỘT lần `run_steps` — **thao tác thật** rồi xác nhận ngay bằng `expect_*` (không cần "nhìn" lại trang). Ví dụ popup quà:
      `{"steps":[{"click":".btn-gift"},{"expect_visible":".MJ__popup-gift"},{"click":".MJ__close-popup"},{"expect_hidden":".MJ__popup-gift"},{"expect_no_console_errors":true}]}`
      Đổi ngôn ngữ EN: `{"steps":[{"click":{"role":"button","text":"EN"}},{"expect_text":".hero__title","value":"..."},{"expect_no_console_errors":true}]}`. DOM đổi đúng / class `active` gắn đúng → khẳng định bằng `expect_count` / `expect_visible` / `expect_attr` trên selector tương ứng.
   3. Form: thử cả input hợp lệ lẫn không hợp lệ (rỗng, sai định dạng) trong cùng `run_steps` — validate phải chặn đúng. Ví dụ input rỗng:
      `{"steps":[{"click":{"role":"button","text":"Gửi"}},{"expect_visible":".error-msg"},{"fill":"#phone","value":"0900000000"},{"click":{"role":"button","text":"Gửi"}},{"expect_hidden":".error-msg"}]}`
   4. `run_script` chỉ dùng để ĐỌC state trang khi `expect_*`/`inspect` không đủ — không dùng để vá hành vi. **Scope là Playwright `page` (Node) — KHÔNG có `document`/`window` trực tiếp**: muốn đọc DOM phải `return await page.evaluate(() => document.querySelector(...)?.textContent)`. Selector mơ hồ (vd `.logo` khớp nhiều element) → thêm scope (`#footer .logo`). FAIL → theo luật **CHỐNG LẶP-FAIL** (không retry cùng kiểu). Bug layout/position/size **KHÔNG** đụng `run_script` — verify tĩnh (xem recipe verify-nhẹ). **run_script KHÔNG có timeout tool-level → PHẢI tự-bound theo luật ⏱** (mọi `page.*` có `{timeout:≤8000}`, `waitUntil:'domcontentloaded'` cấm `'load'`, try/catch + Promise.race 8s; đổi viewport/reload làm bằng `run_steps` chứ KHÔNG `page.reload` — đã treo 190s).
   5. **API thật**: dùng `read_signals` xác nhận request được bắn đi đúng endpoint + lỗi được xử lý gọn (không vỡ UI) — KHÔNG khẳng định server trả đúng. Project có cờ mock (vd `TEST_MODE` của Fox — xem base-structure.md) → bật mock để test trọn luồng.
   6. Khi một bước fail: ĐỌC gói chẩn đoán trả về (console, element gần giống, screenshot path) + dùng `resume_from` để chạy tiếp phần sau, đừng dựng lại cả chuỗi.
   7. Luồng lặp lại nhiều lần (login staging, vào màn cụ thể trước khi test) → lưu bằng `flow` (save), lần sau `flow` (run) — gần 0 token.
   8. Hành vi fail = issue chức năng — popup không mở, form submit không phản hồi là **blocker/major**, không phải minor.
   Mỗi hành vi đã test phải vào mục "Kết quả test chức năng" của report — kể cả PASS, để biết đã phủ tới đâu.
